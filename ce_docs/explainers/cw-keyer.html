Il keyer CW di deskHPSDR

Chi genera gli eventi di manipolazione, chi decide se il keyer gira nella app o nella radio, e come l'uscita del keyer arriva al trasmettitore.

Subject
Cablaggio del keyer CW interno (src/iambic.c) in deskhpsdr

La risposta breve alla tua domanda: oltre al MIDI c'è una sorgente sola, ed è il paddle collegato fisicamente alla radio. Non arriva via MIDI ma dentro i pacchetti di controllo del protocollo HPSDR, e viene instradato al keyer software solo quando la casella «CW handled in Radio» è disattivata. GPIO in questo fork non esiste più.

1. Quale dei due file è «il keyer»

Nel repo ci sono due sorgenti che producono CW, e confonderle è il primo scoglio:

FileCos'èIngresso
src/iambic.cIl keyer — macchina a stati iambic A/B, bug e tasto verticale, con thread dedicatoEventi di paddle (dot/dash, premuto/rilasciato)
src/cw_engine.cMotore testo→CW: ring buffer da 512 caratteri, cw_engine_queue_text()Stringhe da CAT, TCI, terminale

Quello che chiami «il keyer della app» è iambic.c. cw_engine.c è la parte che hai giustamente escluso — è il pezzo che converte testo in CW e che serve CAT e TCI.

Un dettaglio che sfugge: cw_engine.h espone cw_engine_set_terminal(). Esiste quindi una modalità «terminale CW» in cui digiti da tastiera e il testo entra nella stessa coda usata da CAT/TCI. È testo→CW come le altre, quindi fuori dal perimetro della tua domanda, ma è una terza via d'ingresso a quella coda che non passa da nessun rig esterno.

3. Il gate: chi manipola davvero

Tutto ruota attorno a una variabile e a una casella nel menu CW etichettata «CW handled in Radio»:

// iambic.c:268 — dentro keyer_update()
if (cw_keyer_internal == 0) {
  if (!running) { keyer_init(); }   // avvia il thread del keyer app
} else {
  if (running)  { keyer_close(); }  // lo ferma: manipola la radio
}

src/iambic.c:268 · src/cw_menu.c:157

keyer_update() è chiamata a ogni cambio di cw_keyer_speed, cw_keyer_weight, cw_keys_reversed o del gate stesso, e ricalcola le lunghezze in sample:

dot_length  = 1200 / cw_keyer_speed;             // ms
dot_samples = 57600 / cw_keyer_speed;            // 48 kHz · 1200/WPM
dash_samples = (3456 * cw_keyer_weight) / cw_keyer_speed;

src/iambic.c:254-256

Il 3456 è 57600 · 3 / 50: il rapporto dash/dot standard di 3:1 con cw_keyer_weight espresso in percentuale attorno a 50. Cambiare il weight sposta il rapporto senza toccare la velocità nominale.

4. I tre produttori, nel dettaglio

a. MIDI — l'unico che passa dal layer delle action

Un controller MIDI genera un evento, midi3.c lo risolve in una enum ACTION tramite la tabella per nome, e chiama schedule_action(). Qui c'è la scelta di design più interessante del sottosistema:

// actions.c:457 — schedule_action()
switch (action) {
case CW_LEFT:
case CW_RIGHT:
  cw_key_hit = 1;
  keyer_event(action == CW_LEFT, mode == PRESSED);   // IMMEDIATO
  break;
case CW_STRAIGHT_KEY:
  cw_key_hit = 1;
  keyer_straight_event(mode == PRESSED);
  break;
default:
  // tutte le altre azioni: accodate nella idle queue di GTK
  g_idle_add(process_action, a);
  break;
}

src/actions.c:457-495

Le azioni CW sono le uniche a non passare da g_idle_add(). Il commento sopra la funzione lo dice esplicitamente: «CW key actions are processed immediately». La idle queue di GTK gira quando il main loop è libero, con jitter di parecchi millisecondi — accettabile per cambiare banda, letale per la temporizzazione degli elementi Morse. A 25 WPM un dot dura 48 ms; qualche decina di ms di jitter è una manipolazione inascoltabile.

b. Il paddle sulla radio — quello che cercavi

Questa è la sorgente «in più» rispetto al MIDI, e non passa da nessuna action. Lo stato del paddle arriva nei bit del primo byte di controllo del pacchetto HPSDR, decodificato identicamente nei due protocolli:

// old_protocol.c:1673 — Protocol-1
previous_dot = radio_dot;
previous_dash = radio_dash;
radio_dash = (control_in[0] >> 1) & 0x01;
radio_dot  = (control_in[0] >> 2) & 0x01;

// Stops CAT cw transmission if radio reports "CW action"
if (radio_dash || radio_dot) {
  CAT_cw_is_active = 0;
  MIDI_cw_is_active = 0;
  cw_key_hit = 1;
}
if (!cw_keyer_internal) {
  if (radio_dash != previous_dash) { keyer_event(0, radio_dash); }
  if (radio_dot  != previous_dot)  { keyer_event(1, radio_dot);  }
}

src/old_protocol.c:1673-1686 · identico in src/new_protocol.c:3447-3459

Tre cose da notare. Primo: la trasmissione a fronte (!= previous_*) — il protocollo riporta lo stato a ogni pacchetto, il keyer vuole eventi, quindi la conversione avviene qui. Secondo: il gate !cw_keyer_internal è ripetuto anche qui, non solo in keyer_update() — cintura e bretelle, perché il thread potrebbe essere ancora vivo durante un cambio di impostazione. Terzo: toccare il paddle azzera CAT_cw_is_active e MIDI_cw_is_active, cioè il paddle fisico ha sempre la precedenza e interrompe qualunque testo in coda.

c. Il bottone toolbar — presente per omissione, non per scelta

Il dialogo di assegnazione dei bottoni chiama action_dialog_with_hide(dialog, MIDI_KEY, TYPE_HIDE_TOOLBAR, ...), e il filtro è:

// action_dialog.c:78
if (ActionTable[i].type & TYPE_HIDE)  { continue; }
if (ActionTable[i].type & hide_flags) { continue; }

src/action_dialog.c:78-79 · src/toolbar_menu.c:145

In tutta la ActionTable una sola voce porta TYPE_HIDE_TOOLBAR: CW_STRAIGHT_KEY. CW_LEFT, CW_RIGHT, CW_KEYER_KEYDOWN e CW_KEYER_PTT restano quindi assegnabili a un bottone GUI. Non è una funzione: è ciò che resta quando si esclude esplicitamente solo il caso peggiore.

5. L'uscita: non un segnale, due contatori

Il keyer non produce un livello logico. Scrive due interi che sono numeri di sample, e il loop di trasmissione li consuma:

// transmitter.c:1857 — una volta per ogni sample di microfono
cw_not_ready = 0;
if (cw_key_down > 0) {
  cw_key_down--;
  updown = 1;
} else {
  if (cw_key_up > 0) { cw_key_up--; }
  updown = 0;
}

src/transmitter.c:1857-1865

Il vantaggio del disaccoppiamento è che la temporizzazione dell'elemento Morse non dipende più dallo scheduler: una volta che il keyer ha scritto «960 sample di key-down», la durata è garantita dal clock audio, non dal thread. Il thread può anche essere in ritardo — l'elemento in corso esce comunque giusto.

Il valore updown non pilota un interruttore ma un puntatore dentro una rampa precalcolata, cw_ramp_rf[] per l'RF e cw_ramp_audio[] per il sidetone. È la parte che evita i click:

«We HAVE TO shape the signal to avoid hard clicks to be heard way beside our frequency» — commento in transmitter.c:1839.

Un fronte rettangolare su una portante genera uno spettro sinc, con code che si estendono per chilohertz. La rampa è la finestra che confina l'occupazione nella banda del segnale CW. Sidetone e RF hanno rampe distinte perché il primo deve essere gradevole all'orecchio e il secondo deve rispettare lo spettro.

6. Il percorso che scavalca il keyer

Esiste una quarta strada che non tocca iambic.c affatto, ed è quella per i keyer esterni che fanno da sé la temporizzazione:

// actions.c:470 — CW_KEYER_KEYDOWN
// hard "key-up/down" action WITHOUT break-in
// intended for external keyers (MIDI or GPIO connected)
// which take care of PTT themselves.
if (mode == PRESSED && (!cw_keyer_internal || MIDI_cw_is_active)) {
  cw_key_down = 960000;  // max. 20 sec to protect hardware
  cw_key_up = 0;
  cw_key_hit = 1;
} else {
  cw_key_down = 0;
  cw_key_up = 0;
}

src/actions.c:470-483

Scrive direttamente i contatori, saltando la macchina a stati. I 960000 sample sono 20 secondi a 48 kHz: un watchdog contro il tasto incollato, perché senza macchina a stati nessuno garantisce che arrivi il rilascio.

Reliquia da piHPSDR: il commento dice «MIDI or GPIO connected», ma in questo fork src/gpio.c non esiste e nessun header definisce il supporto GPIO per il keying. deskHPSDR nasce come porting macOS/Linux desktop e ha lasciato indietro la parte Raspberry Pi. Se cerchi il percorso GPIO leggendo i commenti lo cerchi a vuoto.

7. Il thread e la sua temporizzazione

Il keyer non fa polling: dorme su un semaforo e viene svegliato dagli eventi.

// iambic.c:325
while (running) {
  enforce_cw_vox = 0;
#ifdef __APPLE__
  sem_wait(cw_event);        // semaforo con nome: macOS non ha sem_init
#else
  sem_wait(&cw_event);
#endif
  // swallow any cw_events posted during the last "cw hang" time.
  if (!kcwl && !kcwr && !external_straight_key) { continue; }

src/iambic.c:325-345

La #ifdef __APPLE__ è la conseguenza del fatto che macOS deprecò i semafori POSIX anonimi: sem_init() esiste ma ritorna ENOSYS, quindi serve sem_open() con un nome. Dentro il loop la temporizzazione degli elementi usa clock_nanosleep() in modalità assoluta — anch'essa assente su macOS e fornita da uno shim in src/MacOS.h.

Vale la pena saperlo perché è codice ancora in movimento: il commit 328a431 del 2026-08-30, cioè l'HEAD attuale del fork, corregge proprio quello shim — «Return immediately when the requested absolute time has already passed instead of generating an invalid relative sleep interval». Un tempo assoluto già passato produceva un intervallo relativo negativo, e quindi un'attesa sbagliata dentro la temporizzazione del keyer.

8. Il flag che tiene in ordine le priorità

cw_key_hit compare in ogni percorso visto finora. Non è uno stato di manipolazione: è un segnale di aborto verso i motori testo→CW. cw_engine.c lo controlla prima di ogni singolo elemento:

// cw_engine.c:51, ripetuto in ogni send_dot/send_dash/send_space
if (cw_key_hit || cw_not_ready) { return; }

src/cw_engine.c:51-93

Il controllo è ripetuto a ogni elemento e non una volta per carattere: se metti mano al paddle mentre la radio sta mandando un CQ da macro, la trasmissione si interrompe entro un punto, non a fine parola. È la regola implicita di ogni stazione — la mano sul tasto vince sempre sull'automatismo — realizzata come guardia in tre righe.

9. Il sidetone locale

Il keyer deve produrre un tono che tu senti, e la domanda non è banale perché la radio ne genera già uno per conto suo. La ragione per cui serve quello locale è operativa, non tecnica: quando il rig è fisicamente in un'altra stanza rispetto al PC, il sidetone dell'FPGA esce da un altoparlante che non è dove stai manipolando. L'unico tono utile è quello che esce dalle cuffie attaccate al computer.

deskHPSDR genera due toni distinti, con accumulatori di fase separati:

// transmitter.c:1709 — tono SPEDITO ALLA RADIO nello stream IQ
sidetone = sidevol * ramp * sine_generator(&p1radio, &p2radio, cw_keyer_sidetone_frequency);

// transmitter.c:1898 — tono LOCALE
cwsample = 0.00196 * vol * val * sine_generator(&p1local, &p2local, cw_keyer_sidetone_frequency);
if (active_receiver->local_audio) { cw_audio_write(active_receiver, cwsample); }

src/transmitter.c:1709, 1898-1915

Gli accumulatori separati non sono ridondanza. Se i due toni condividessero lo stato di fase si contenderebbero l'avanzamento quando sono attivi entrambi, e sentiresti battimenti.

Un anello dedicato, non il buffer della ricezione

Il sidetone locale non passa dal ring audio della RX. Ha il suo (rx->sidetone_buffer, puntatori atomici, singolo produttore e singolo consumatore senza lock), drenato dalla stessa callback CoreAudio ma in modo indipendente, e sommato in coda su entrambi i canali:

// macos_audio.c:634 — dentro la render callback
if (st_in != st_out) {
  sidetone = st_buffer[st_out];
  st_out++;
  // ...
}
left  += sidetone;
right += sidetone;

src/macos_audio.c:612-645

La separazione è ciò che permette al tono di avere una latenza propria, molto più bassa di quella della catena di ricezione, che invece è dimensionata per assorbire il jitter di rete verso la radio.

Il controllo di latenza, e perché macOS è un caso a parte

La versione ALSA riavvolge il buffer di riproduzione alla transizione RX→TX con snd_pcm_rewind(). CoreAudio non ha un equivalente, quindi macos_audio.c gestisce la latenza con un controllore esplicito:

CostanteSample@ 48 kHzRuolo
CW_LAT_LOW1282,67 mssotto questa soglia inserisce uno zero
CW_LAT_TARGET2565,33 msriempimento all'avvio della TX
CW_LAT_HIGH3848,0 mssopra questa soglia scarta un sample

src/macos_audio.c:152-154

Alla transizione RX→TX l'anello viene inizializzato esattamente a CW_LAT_TARGET, senza ereditare il riempimento del ring RX. Poi ogni 16 sample il controllore corregge la deriva fra il clock del produttore e quello del dispositivo. La finezza sta in una riga:

// macos_audio.c:1132
if (sample != 0.0f) { count = 0; }   // il contatore si azzera sul tono

Il contatore che abilita le correzioni si azzera a ogni sample non nullo. Le correzioni possono quindi scattare solo nei silenzi fra gli elementi, mai dentro un dot o un dash. È un trucco che vale la pena rubare: invece di rendere le correzioni più piccole, le sposta dove sono inudibili.

Il buffer CoreAudio, e perché è già stretto. L'AudioUnit non vive in macos_audio.c (che gestisce solo gli anelli) ma in coreaudio.c, dove coreaudio_tune_buffer_frames() interroga kAudioDevicePropertyBufferFrameSizeRange, clampa la richiesta e imposta kAudioDevicePropertyBufferFrameSize. Il target in uscita è COREAUDIO_OUTPUT_BUFFER_TARGET 128 (coreaudio.c:39), cioè 2,67 ms a 48 kHz — valore da DAW, non default di sistema. Il totale realistico del sidetone locale è quindi 5,33 ms di anello più 2,67 ms di buffer più la latenza del DAC: circa 9-11 ms, nella stessa fascia del sidetone generato dalla radio via P2 (17 ms misurati su ANAN-7000, new_protocol.c:3535). La dimensione è una proprietà del device, non del client: 128 è una scelta deliberatamente educata, perché scendere più giù la imporrebbe a tutto ciò che suona sullo stesso dispositivo.

Due vincoli strutturali

Il primo: tutto il blocco vive dentro if ((txmode == modeCWL || txmode == modeCWU) && radio_is_transmitting()). Il sidetone non esiste prima che il TX sia effettivamente su, quindi sul primo elemento in break-in si somma l'intera transizione RX→TX, round trip verso la radio incluso. Dal secondo elemento in poi la TX è già attiva e conta solo la latenza audio.

Il secondo: la generazione locale è condizionata a active_receiver->local_audio. Se l'ascolto passa dall'uscita audio della radio anziché dal computer, la app non produce alcun tono — e in quella configurazione è corretto così, perché il tono lo fa l'FPGA.

Le due cose si incastrano con il gate della sezione 3. Con cw_keyer_internal attivo la app spedisce silenzio e lascia fare all'hardware:

// transmitter.c:1930
if (!cw_keyer_internal || CAT_cw_is_active) { s = (int)(cwsample * 32768.0); }
new_protocol_cw_audio_samples(s, s);   // s == 0 se il keyer sta nella radio

Quindi la scelta non è fra due implementazioni dello stesso tono, ma fra due posizioni: sidetone nell'FPGA quando sei accanto alla radio, sidetone nella app quando la radio è altrove. La latenza è il prezzo della seconda, e i 5,33 ms di anello sono lo sforzo di tenerlo basso.

Se dovessi aggiungere una sorgente di manipolazione — per esempio una seriale, o un'interfaccia di rete — il punto d'innesto corretto è keyer_event(left, state) con conversione a fronte a monte, non i contatori. I contatori sono per chi ha già la propria temporizzazione.
